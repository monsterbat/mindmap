# DESIGN.md — mindmap 架構與設計邏輯

> 2026-07-30 訪談定案,2026-08-02 依使用者實際使用回饋大改。
> **本檔是「為什麼這樣設計」的正本**;逐步經過與修正記在 `CHANGELOG.md`,動手前的硬規則在 `CLAUDE.md`。

## 一、產品定位

使用者與 AI 用「同一份心智圖」溝通的工具,解決兩個痛點:

1. **架構討論很亂**:條列式越長越難表達「這個分支牽連到那個項目」;AI 手刻 HTML 圖使用者改不了,溝通是單向的。
2. **使用者的思考邏輯傳不進 AI**:規劃、優先順序、排程的關聯結構,用圖遠比用文字準。

目標:**AI 畫得出來、使用者改得動、改完 AI 讀得懂**——雙向共編。未來做得好可開放他人用,第一階段純自用。

## 二、核心心智模型:一張圖上有三種東西(2026-08-02 定案)

這是整個設計的地基,所有 UI 決策都從這裡推出來。

| 種類 | 放哪裡 | 為什麼 |
|---|---|---|
| **概念結構** | **子節點** | 「這個東西是由哪些部分組成的」。例:To-do list → 階段性目標 / 優先序。這是心智圖的本體,要一眼看得到 |
| **說明** | `detail.explain` | 「這是什麼、為什麼這樣定」。給使用者回頭看,也**給 AI 當判斷依據** |
| **待辦** | `detail.todos[]` | 「要做完哪些事,這個節點才算完成」。每項有自己的等級與狀態 |

**為什麼待辦不開成子節點:** 使用者的需求(2026-08-02)——待辦開成子節點會把心智圖塞滿(概念結構被任務淹沒),但寫成純文字又「不會體現出它是要做的事,橘色點點不見了」(失去等級與統計)。所以走第三條路:**待辦是節點的欄位,不佔版面,但照樣被統計**。

### 資料模型

```json
{
  "id": "…",
  "topic": "🔜 標題",                        // 開頭圖示=狀態
  "tags": ["P2", "等回覆後"],                // P1–P4=艾森豪等級,其餘=自由標籤
  "detail": {
    "explain": "這是什麼、為什麼這樣定",
    "todos": [{ "text": "要做的事", "st": "⏳", "p": "P1" }]
  }
}
```

- **狀態**寫在 `topic` 開頭圖示——刻意放在標題裡,因為**圖上要一眼看到**。
- **等級**用 `tags` 的 P1–P4,對應 Workspace 的艾森豪矩陣規則。
- **統計徽章** `📝 🔴2 🟠1`:往下數所有「狀態不是 ✅」的節點與待辦,依等級分組。⚫=還沒標等級。

### 狀態:節點與待辦共用同一組詞彙(2026-08-02 定案)

`⏳`待辦 / `🔜`進行中 / `⏸️`等別人 / `✅`完成(節點另有 `🎯`目標)。

**為什麼統一:** 原本待辦只有「勾/沒勾」,節點卻有四種狀態。使用者一眼看穿:「這個項目點開來可以設狀態跟等級,下面的待辦只有等級,**這樣子的操作邏輯是不是有點資訊落差**?」是。二元的勾選框把「談完了、簽完了、在等對方、還要回頭驗證」整段過程壓扁成一格「沒勾」。

**為什麼多一個 `⏸️ 等別人`:** 使用者舉的原案例(要對方把紙本改成電子版)最關鍵的一段就是「文件簽完了,球在對方那邊」。這跟「球在我這」在排程上是完全不同的處置——使用者的艾森豪矩陣規則與每日報告都要分得出「等你」與「等別人」,否則會一直催一件他動不了的事。⏸️ **照樣算未完成**(它確實還沒好),但統計行另外標「其中 N 件在等別人」,待辦列用虛線框弱化。

**一件事有好幾步怎麼放** —— 判斷線是「步驟要不要各自被追蹤」:

- 步驟 ≤ 3 且不用各自追蹤 → 留成一條待辦,用狀態表達進度
- 每步各有時間點 / 各自可能卡住 / 要各自標等級 → **升成子節點**,步驟變它的 todos,節點狀態=整件事的進度

⛔ 不做巢狀待辦。理由:那等於在心智圖裡蓋一個小型任務管理器,跟「心智圖=結構與脈絡的視圖」的定位打架,而且統計要多算一層。現有模型(節點+待辦兩層)已經夠表達多步驟的事。

**待辦全完成時只提示、不自動改節點狀態**——面板出現「待辦 3/3 都完成了 — 把這個節點標成 ✅」按鈕,按了才動。自動改內容跟自動改外觀是同一種病(見 §五 原則 1)。

## 三、系統架構

```
瀏覽器(使用者編輯) ──HTTP── 心智圖伺服器(:8030) ──讀寫── Workspace/mindmaps/*.json ──Read/Edit── AI
```

| 決策 | 內容 | 為什麼 |
|---|---|---|
| 正本 | 一圖一份 JSON,git 追蹤 | 人用圖形編輯器、AI 用文字工具,共編同一份;diff 可讀 |
| 排版 | **結構式心智圖,不是自由畫布** | 檔案只存結構,位置引擎自動算 → AI 不用算座標,大圖不會疊成一團 |
| 引擎 | mind-elixir(MIT、零依賴) | 拖拉/關聯線/顏色/標籤/摘要/undo 全現成 |
| 格式 | mind-elixir 原生 JSON + 自訂 `detail` 欄位 | 少一層轉換=少一類 bug |
| 前端 | 原生 JS + vendor UMD,無 build step | 環境重建=zero |
| 後端 | 純 stdlib `http.server`,**系統 `/usr/bin/python3`**,port 8030 | launchd + TCC 只放行系統 python3(brain 同款配方);2026-07-31 從 FastAPI 改過來 |
| 資料 | `Workspace/mindmaps/*.json` | 跨領域思考的內容,跟 Workspace git 同步兩台 |

### `/day` 排行程的設計(2026-08-11)

`/day` 排行程(2026-08-24 前叫「排今天」,⛔ 路徑不改)= **手拖的排程器**(左邊一天的直式時間軸、右邊還沒做完的任務)。
使用者的需求(2026-08-11):「它卻死在那邊什麼都動不了,那我要它幹嘛?」「我想設計一個更好讓我去
做拖拉行程的工具。」`/plan` 是**算出來的**建議,`/day` 是**他自己排**的 —— 兩者互補。

| 東西 | 存哪 | 為什麼 |
|---|---|---|
| 任務的「哪天幾點做」 | 心智圖節點 `detail.planned`(**陣列**)| 使用者選的:任務板上要看得出「已排 8/12 早上」 |
| 日常區塊的**範本** | `排程設定/日常區塊.json` | 吃飯/語言/讀書/運動/通勤,拖了不消失 |
| 日常區塊的**實例** | `排程設定/每日行程/<日期>.json` | ⛔ 不進心智圖 —— 圖會被吃飯通勤淹掉 |

**一件事可以切成好幾段排**(2026-08-11)。`detail.planned = [{uid, at, min}, …]`。
舊格式(單一 `plannedAt`/`plannedMin`)讀取時自動轉成一段,不需要先跑遷移。

**⛔ 排行程完全不看 `effort`(2026-08-30 定案,推翻 2026-08-11 的額度制)。**
使用者的需求是:「我根本沒有辦法知道我要花幾個小時完成,那我就變成會限制我在安排時間的長度,
而且如果今天真的比較長、我想拆兩天的話還沒辦法弄。」

| | 舊(2026-08-11〜08-29) | 新(2026-08-30 起) |
|---|---|---|
| 右邊那一區的意思 | 還沒排掉的**時數** | 還沒做完的**事** |
| 排進行程之後 | 額度扣完就從右邊消失 | **不會消失**,可以一直拖 |
| 一塊多長 | 剩下的額度 | 一律預設 60 分,自己拉長縮短 |
| 什麼時候離開右邊 | 排滿了 | **只有標 ✅ 完成** |
| 右邊卡片上的領域 | 只有顏色 | **2026-09-17 起用字標在等級後面**(使用者:「直接看的時候我會知道這個東西是屬於什麼領域的」)。顏色記不住 |
| 已完成的方塊 | — | 留在原時段當紀錄:✅ + 淡色 + 標題劃掉 + 完成日,**預設就看得到**(頂列「顯示已完成」可關)。**2026-09-17 起跟沒做完的一樣能按 ✎ 打開、能拖、能拉長度、能按 ✕ 拿掉**;按 ✎ 裡的「⏳」改回沒做完 |

- **好處**:同一件事可以在一天的不同時段各放一塊、也可以跨好幾天,而且拖到哪天都不必先猜總時數。
- **代價**:右邊那一區只會長不會短,**除非他按完成**。⛔ 沒有第二個出口是刻意的 ——
  舊制那個「排滿就自動消失」的出口正是他找不到任務的原因(2026-08-24 那次盤點有 11 件)。
- **⚠️ `effort` 欄位刻意沒有刪掉**:心智圖與任務板還改得到,`/plan` 行程表還在讀它。
  使用者(2026-08-30):「/plan 這個我覺得不用管他,反正我好像也都沒有在用他的。」
  ⛔ 不要因為排行程不看它就把欄位拔掉 —— 那會連 `/plan` 一起弄壞,而他沒說要那樣。

**⛔ 拖拉一律走 `PATCH /api/maps/<圖>/nodes/<id>`,不是 PUT 整張圖。**
300 個節點每拖一下重寫一次,他同時開著心智圖網頁幾乎一定撞 409,
每拖一次跳一次「圖被別人改過了」→ 那個工具就沒法用。
PATCH 只准動 `PATCHABLE` 那幾個排程欄位(它沒有衝突偵測,能改的越少誤傷越少)。

### 同一份圖,四個看法(2026-08-08 定案;2026-09-08 加 `/topics`、收掉 `/plan`)

| 頁 | 回答的問題 | 誰寫回 |
|---|---|---|
| `/` 心智圖 | **結構** —— 什麼跟什麼有關、為什麼這樣定 | 讀寫(使用者拖拉、AI 用 mm.py) |
| `/board` 任務板 | **狀態** —— 哪些沒做、做到哪、什麼等級 | 只改狀態(走同一個 API) |
| `/day` 排行程 | **他自己排的時間** —— 哪天幾點做哪一塊 | 拖進時間軸 → `detail.planned` |
| `/topics` 待辦事項 | **「這件事我還剩什麼沒做」** —— 按主題收起來 | 打勾改狀態、直接新增待辦 |

#### `/topics` 待辦事項(2026-09-08)

使用者的回報(2026-09-08):「我們現在每次處理什麼事情都會產生一大堆待辦事項,但是這些待辦事項
我到最後其實都不知道我到底還需要做什麼,那每次都還要再跑去心智圖那邊去看有缺什麼,
這樣其實很煩躁…**我們沒有一個我自己可以去檢視審查的環境,我這樣很容易漏掉很多事情。**」

**它跟任務板的分工:任務板把所有任務攤平依「狀態」分四欄,回答得了「有哪些事」;
待辦事項頁按「主題」收起來,回答「這件事我還剩什麼沒做」。** 當時圖上有 112 件
未完成待辦攤成一片 —— 那個數字本身就是他找不到東西的原因。

| 決定 | 選了什麼 | 為什麼 |
|---|---|---|
| 主題怎麼認定 | **自動**:非待辦節點 + 底下(含子孫)有 ≥2 件待辦 | 使用者 2026-09-08 選的。手動標的話,「忘記標」就會漏 —— 而漏東西正是這頁要解決的病 |
| 收了之後還往下找嗎 | ⛔ 不找 | 不然同一批事情會在祖先跟後代各出現一次 |
| 領域算主題嗎 | 不算,它是分類 | 領域底下什麼都有,收成一個主題等於沒收 |
| 沒歸到主題的怎麼辦 | 每個領域一個「零星待辦」桶 | ⛔ 不能讓它們無家可歸 —— 那就是他現在漏東西的成因 |
| 層面(主題底下的分組) | **扁平化**,名字寫成路徑 | 巢狀太深看不完;縮排只有一層 |
| 已完成的 | 顯示,但沉到每組最下面、整組做完的沉到最底 | ⛔ 不隱藏(同 `/day` 2026-08-30 的規則:他要看得到自己做過什麼) |
| 一行的欄位順序 | **把手 → 優先區 → 分類 → 主題名 → 死線 → 進度** | 使用者 2026-09-08 第二輪定的:「第一個就是優先區、再來就是分類、再來才是內容」。用 grid 不用 flex —— 前三欄固定寬度才對得齊,一整欄掃下來才快 |
| 預設排序 | **等級 → 死線 → 還剩幾件** | 艾森豪:重要先於緊急。⛔ 不是「死線優先」——「明天到期但沒卡人」是 P3 |
| 他自己拖的順序 | 存在節點的 `detail.viewOrder`,走 `PATCH /api/maps/<圖>/view-order` | ⛔ 不用 PUT 整張圖:拖一次要重編 20 幾個節點,而他常同時開著心智圖 → 幾乎一定撞 409 |
| 拖曳的機制 | **pointer 事件自己做**,⛔ 不用 HTML5 drag-and-drop | ①手機與平板的瀏覽器完全不支援 DnD ②`draggable` 一設下去標題文字就選不起來 |
| 反悔 | 頂列「↺ 順序改回自動」清掉所有 `viewOrder` | ⛔ 一個「只進不出」的排序他不敢亂拖 |

- **收起來的時候也要有資訊**:進度條(`3/12`)、最近的死線、**下一件該做的是什麼**
  —— 不展開就能決定要不要動它。
- **可以直接打勾、直接新增。** 使用者的痛點是「想到一件事 → 要回去叫 AI 加 → 沒加 → 忘記」,
  少掉中間那兩步才有可能把腦子裡的東西倒出來。新增的那條 `explain` 會寫明
  「使用者自己在待辦事項頁加的(還沒寫為什麼要做)」,想補的時候找得到。
- 網址參數 `?open=<id,id>&domain=<領域>&q=<關鍵字>` 可以一進來就展開指定主題
  —— 心智圖或早報要把他直接送到某一個主題時用。

**怎麼驗:`make verify-topics`**(開真的瀏覽器點過一輪,用正式圖的複本+臨時埠)。
⭐ 第一項就是**分母對帳**:把圖上真正有幾件待辦印出來,跟畫面上看得到幾件對
(Workspace CLAUDE.md「⛔ 要掃過全部的工具不准用白名單」那條)。
**這一頁最不能犯的錯是安靜地漏掉幾件** —— 而「漏掉」在畫面上長得跟「本來就沒有」
一模一樣:沒有錯誤訊息、沒有紅字、數字看起來也很合理。
靜態的那幾條在 `tests/test_topics_route.py`,`make check` 就會跑。

#### 📐 四頁的介面規範(2026-09-09 定,MUST)

使用者的回報(2026-09-08):「我按了心智圖、按了待辦事項、按了排行程,**他的介面都長得不一樣,
然後會跳來跳去,他的擺放位置也會跳來跳去**,這樣真的很奇怪。我希望你就是都在固定位置
不要跳來跳去。**你這個心智圖如果它有比較多的功能,你應該把那些功能放在往下面的一排**,
而不是讓他上面第一排的選擇東西跳來跳去亂七八糟的。」

⭐ **根因不是誰寫歪了,是「沒有共用的那一份」。** 導覽列本來四頁各寫各的
(四個 html + 四個 css),於是同一顆「任務板」按鈕在排行程頁是第 3 個、
待辦事項頁是第 2 個、心智圖頁是第 5 個 —— **每加一頁就多歪一次**,
2026-09-08 我加 `/topics` 的時候又歪了一次。

| 規則 | 內容 |
|---|---|
| **第一排只放分頁** | 順序固定:🧠 心智圖 → ✅ 待辦事項 → 📋 任務板 → 🗓 排行程(範圍由大到小:整張圖 → 我還剩什麼 → 哪些在進行 → 今天幾點做) |
| **當前頁不准拿掉** | 改成亮起來。⛔ 拿掉的話剩下幾顆的位置每頁都不同,那正是他抱怨的「跳來跳去」 |
| **狀態列固定在第一排最右** | `#status` 由 `nav.js` 生,四頁位置一致。⚠️ id 不能改,各頁的 JS 都是 `getElementById("status")` |
| **第二排放這一頁自己的工具** | 左邊篩選、右邊搜尋。四頁的第二排樣式也統一(透明底+邊框) |
| **正本只有一份** | `static/js/nav.js` + `static/css/nav.css`。⛔ 各頁不准自己寫 `href="/board"` 這種分頁連結 —— `tests/test_day_route.py::test_MUST_分頁連結只有一份正本` 會擋 |
| **高度不准寫死** | `--nav-h`(nav.css)與 `--tool-h`(app.css)。⛔ 心智圖畫布有 4 個 `calc`,寫死的話少改一個就多一條捲軸或切掉底部,而且不報錯 |

**怎麼驗:`make verify-nav`。** 它比的是**渲染後的像素座標**不是原始碼 ——
同一份 `nav.js` 被某頁的 CSS 蓋掉位置,讀原始碼是看不出來的。
2026-09-09 實測四頁的四顆按鈕左邊界都是 `[11, 104, 210, 303]`。
它同時點過心智圖那 4 個搬到第二排的工具:**按鈕失效不會報錯**,畫面一模一樣只是按了沒反應。

#### 新增待辦的入口:原本四頁只有一頁加得了 → 右下角「＋」(2026-09-17)

使用者的需求(2026-09-17):「有時候我突然想到一些任務、一些想要做的事情,好像就沒有辦法直接加在我們這個上面。」
盤點結果(讀程式碼,不是憑印象):

| 頁 | 能不能新增 | 怎麼加 / 為什麼不行 |

## 三之二、資料怎麼流:讀是自動的,寫是人工的(2026-08-07 定案)

使用者 2026-08-07 問:「所以你的方法是讓系統更加自動化嗎?會有程式去抓取每一個專案的待辦事項嗎?」
答案是**一半**,而且另一半是**刻意不自動**的。

### 誰是誰的正本(⛔ 一件事只有一個家)

| 東西 | 正本 | 誰寫 |
|---|---|---|
| 任務、計畫、架構、規則的地圖 | `Workspace/mindmaps/全局總覽圖.json` | 使用者(瀏覽器)+ AI(`mm.py`) |
| 某專案自己的 commit 級細項 | 該專案 `TODO.md` 的手寫區 | 該專案的對話 |
| 事實、規則、SOP | `notes/*.md`、各層 `CLAUDE.md` | 寫的人 |
| 已完成的一次性事件 | `Workspace/notes/完成紀錄.md` | 收工時移過去 |

### 三條資料流

1. **拉(自動,每分鐘)**:圖上掛了 `source` 的節點 → 伺服器 `/api/project` **即時去讀**那個資料夾的
   `TODO.md`/`CHANGELOG.md`,算出「還有幾件沒做」畫成 `⟳n` 徽章。⛔ **不寫回 JSON**。
   主控台的「專案現況」頁(`brain/build_plan.py`)同一招。
2. **推(人工,靠規則與工具)**:計畫變動/新增、系統變更 → AI 用 `mm.py` 寫進圖(全域 §十九)。
   ⛔ **沒有「自動把專案待辦抓進圖」這回事** —— 專案有上百條 commit 級細項,全搬會把圖淹掉。
   圖上只放「要在全局視野看到的」,其餘靠 `⟳n` 知道還剩多少。
3. **對帳(半自動)**:`sync_todos.py` —— **文字單向(圖說了算)、打勾雙向**。
   圖上的待辦會生成到專案 `TODO.md` 的 `mm:begin/end` 同步區;在那裡打勾會回寫成 ✅ 並圈起來。

### 為什麼讀自動、寫人工

「還有幾件沒做」是**機械可算**的事實 → 交給機器,而且用拉的(不複製就不會 drift)。
「這件事重不重要、屬於哪個項目、要不要進全局視野」是**判斷** → 沒有判斷力的自動化只會製造垃圾。
所以不做全自動抓取,改成把判斷的成本壓到最低:`mm.py` 一行指令 + 寫入前自動體檢 + 自動圈起來。

### 三道保底(規則沒人查等於沒有)

| 機制 | 抓什麼 | 什麼時候跑 |
|---|---|---|
| `lint_map.py` / `mm.py lint` | 結構違規:待辦沒等級、項目掛等級、待辦沒狀態、指針斷鏈、說明藏待辦 | 動完圖;`mm.py` 每次寫入前自動跑 |
| 圖上的「對帳:N 天前」 | 超過 7 天沒跟專案 TODO 對過帳 | 一直顯示 |
| 週日重排(每週的排程腳本) | 這週推了什麼、下週主線 | 每週日 20:00 |

**還沒有的:漏寫偵測** —— 沒有東西會在「AI 忘了把新決定寫進圖」時抓包。
可行做法:週日掃各專案 CHANGELOG 的新條目,比對圖上有沒有對應節點,只報異常。

## 四、UI 分層:內容與外觀分開(2026-08-02 定案)

**點節點 = 看/編內容,不跳出任何外觀設定。**

- **右側詳情面板(常駐,版面固定)**:狀態、等級、自由標籤、說明、待辦清單。點節點直接換內容,不必先按按鈕。
- **「🎨 外觀」模式(預設關)**:開啟後點節點才跳出引擎原生的顏色/字級面板(含清除字色/底色/全部/便條樣式)。

**為什麼分開:** 使用者的需求「我點一個節點會同時跳出詳情和顏色設定,很不直覺」;而且**內容不能被鎖在外觀模式後面**——出過兩次問題(P1/P2 找不到、自由標籤刪不掉)。

### 節點上的東西全部排一行(2026-08-03 定案)

使用者:「加了等級之後,原本一行好好的變成三行 —— **我要他一行就完成所有的內容**」。

原因是引擎把 tags 畫成 `<div class="tags">`,**div 是區塊元素一定自己占一行**,徽章的 `::after` 又排在它後面。`.tags` 改 `display:inline` 就全部流回同一列。**版面是心智圖的命脈**:節點一高,整張圖的行距全被撐開,能一眼看到的範圍就變小。

一行裡由左到右:

| 位置 | 內容 | 為什麼在那裡 |
|---|---|---|
| 開頭 | 狀態圖示 + 標題文字 | 本體,前面不放任何東西(使用者:「放在前面很怪」) |
| 接著 | `P2` 等級 + 自由標籤 | 等級=紅橘黃灰、自由標籤=藍,**顏色本身就分得出這兩種東西** |
| 再來 | `📝 🔴2` | 有詳情 + 底下還沒做的事 |
| 最後 | 紅牌 `⇄n` | 連著幾條關聯線。**紅色跟關聯線同色**,掃一眼認得出樞紐 |

⚠️ 一個元素只有 `::before`(前)與 `::after`(後)兩個位置,但徽章跟紅牌**都要在後面**。
所以 `me-tpc` 改成 `inline-flex`,用 `order` 把 `::before` 排到最後 —— 這也順便解決了 tags 占一行的問題。`flex-wrap: wrap` 要留著,長標題還是得折得下去(有測)。

**等級為什麼要換色:** 引擎預設四個等級長得一模一樣(同一種藍底),看了等於沒看;而且跟統計徽章的 🔴🟠🟡⚪ 對不起來。CSS 選不到文字內容,所以由 `markPriorityTags()` 標 `data-p` 再上色 —— 它畫的是「等級」這個系統欄位,不寫進 `node.style`,跟被禁的「依內容自動改外觀」是兩回事(見 §五 原則 1)。

### 連到別張圖:節點的 `hyperLink`(2026-08-03 改)

引擎原本只在標題後面畫一個很小的 🔗,而且**介面上設不了**(只有改 JSON 一途)。使用者:「我哪知道要點後面的🔗」。

- 小 🔗 換成藍色 **「開啟 ↗」膠囊**,節點加虛線底線 —— 看得出這是連結。
- **點膠囊 = 一下就開;點節點本體要「已經選起來」才開。**
  > ⛔ 一開始做成「點哪裡都直接開」,結果**這個節點永遠選不起來、連結也拆不掉**(每次想選它都被送去別張圖)。用捕獲階段的 `pointerdown` 記下「按下去的當下選了沒」——等到 click 事件時引擎早就把它設成 selected 了。
- 雙擊要改字 → `dblclick` 進來就取消跳轉;編輯框開著時一律不跳。
- 面板有下拉可以自己設/拆。**清除要走「動資料 + `refresh`」**,`reshapeNode` 是 `Object.assign` 清不掉既有欄位。

### 關聯線(紅線):資料一份,顯示三檔(2026-08-03 定案)

**關聯只有一份資料 = `arrows` 的 `from`/`to`/`label`。** 線、面板清單、節點上的 `🔗n` 徽章都是同一份資料的三種畫法。

**⛔ 不另外做「連結」欄位。** 使用者 2026-08-03 問「關聯線拉來拉去會非常的亂,有沒有辦法使用連結的方式」——**亂的是畫法不是資料**。真的開第二套欄位,同一個關係會記在兩個地方遲早對不起來,而且會失去引擎「右鍵連接、拉一下就好」的原生操作。他問的「點了跳過去」與「用到才彈出線」,其實是同一個功能的兩面。

| 檔 | 畫面 | 什麼時候用 |
|---|---|---|
| 全開 | 所有線都畫 | 想一眼看全圖有哪些牽連 |
| **聚焦(預設)** | **只畫跟目前選取節點有關的線** | 平常。線再多都不亂 |
| 全關 | 一條都不畫 | 專心看結構 |

- 工具列「🔗 線」循環切換,記 localStorage;**純顯示層,不動資料**。
- 全關時三層一起藏:線本體 `.topiclinks`、控制點 `.linkcontroller` 與 `.circle`、標籤 `.svg-label[data-type="arrow"]`(摘要的標籤不受影響)。
- 聚焦時**不藏控制點**——亮著的那條線照樣要點得到、拉得彎。
- ⚠️ **引擎在「選取一條線」時會先 `clearSelection()` 清掉節點選取**。聚焦模式不特別處理的話,線會在手指底下消失、剛拉好的新線也會馬上不見。解法:`linkController` 顯示中 = 有線正在編輯,那條一律留著。

**詳情面板的「🔗 關聯」段**:列 `← 誰餵給我` / `⇄ 雙向` / `→ 我餵給誰` + 線上的標籤,**點名字就跳到對方節點**(選取 + 捲過去 + 閃一下)。跳過去之後對方的線又亮出來,所以**可以一路點著把整條資料流走完**(使用者舉的例子:儀表板 → 某個投資分析 → 日報)。線全關時這裡是唯一入口;而且**指進「收起來」分支的線根本畫不出來**,所以關聯不能只畫在圖上。

### 關聯線就地改,不用重拉(2026-08-03)

方向慣例訂下來之後,使用者要把既有的線全部對調:「**一個一個去重拉很麻煩**」。所以每一列都給三個操作:

| 鈕 | 做什麼 | 注意 |
|---|---|---|
| 文字框 | 改 `label` | 打字當下就改,圖上的字同步換 |
| `⇅` | 調轉方向(`from`/`to` 對調) | **`delta1`/`delta2` 要跟著換邊**,不然他手拉的彎度會扭掉 |
| `⇄` | 單向 ⇄ 雙向 | 改回單向要**把欄位刪掉**,`reshapeArrow` 是 `Object.assign` 清不掉 |

- 三個都走引擎的 `reshapeArrow`:就地重畫、記進 undo、fire `operation` 讓自動存檔接手。⚠️ 它內部用 `findEle`,對方被折疊起來會 throw → 要接住並退回「改資料 + `refresh`」。
- 雙向時 `⇅` 停用(沒有方向可調)。
- **清單只在 `createArrow`/`removeArrow` 時重畫**——每種 operation 都重畫的話,在標籤輸入框打字會被自己打斷。

**線也可以拉彎**:點一下紅線 → 出現兩顆灰色控制點 → 拖它們,曲線就繞開擋到的字。彎度存在 arrow 的 `delta1`/`delta2`,是資料的一部分,會跟著存檔。

## 五、設計原則(踩坑換來的,MUST)

1. **⛔ 不准做「自動改」的隱形規則——外觀如此,內容更是如此。** 一律:①使用者明確操作觸發 ②寫進節點自己的資料 ③改得掉。看到什麼就是什麼;程式最多**提示**,不替他決定。
   > 曾做過「topic 開頭是 📏 就自動套便條樣式」+3 秒計時器 → 使用者只想改底色卻連字級斜體邊框一起被改、清掉又自己回來、關不掉,連續回報三次「怎麼改都跳回去」。
   > 同理:待辦全 ✅ 了也不自動把節點標成 ✅,只在面板給一個按鈕。
2. **會出現在圖上的資料,詳情面板就必須能編也能刪。** 不准把內容類設定放進外觀模式。
3. **⛔ 測試不准碰正式圖**,一律用 `_沙盒`;也不准用腳本整檔覆寫正式圖(要改用精準的單節點編輯)。
   > 曾經出過的問題:Playwright 測試「整張載入→改→整張存回」把使用者同時在另一台上的編輯洗掉。
4. **改版面寬度就要重新置中**(徽章撐寬、開關面板、視窗縮放)。
5. **`mind.getData()` 回的是深拷貝**——要改活的節點一律走 `mind.findEle(id).nodeObj`。
   - ⚠️ **`findEle` 找不到是 throw,不是回 null**(節點被折疊、剛換過圖都會遇到)。一律走 `eleById()` 接住;只要讀資料就用 `nodeDataById()`(走 `getObjById`,折疊起來也讀得到)。
   - 引擎會**默默丟掉**兩端不存在的關聯線(`tidyArrow`,每次載入),**指進折疊分支的線則是畫不出來**(`renderArrow` 內部 throw 被自己 catch)。所以關聯不能只畫在圖上——詳情面板那份清單是它的保底。
6. **vendor 檔的修補要記在 `static/vendor/PATCHES.md`**,升版時重套(目前 5 處:節點顏色/字級不在內建清單時面板會崩潰)。
